## Текущая функциональная база

- **Trade:** Ardent, единое рабочее окно, one-way/round-trip/continuous/cargo-sale, поиск товара, закрепление, фактический прогресс и история. Оценки времени, profit/hour, confidence и рисков уже существуют.
- **Mining:** prospector advice, адаптивный порог, loadout/collectors/limpets, сессии и экономика, поиск мест, личная история кольца, связка Mine → Sell, MFD/LED-подсказки.
- **Engineering:** inventory, wishlist, отдельное отслеживание материалов, путь грейдов, чертежи инженеров, рекомендации/вики, поиск material traders и передача системы в навигацию.
- **Exploration/exobio:** каталог, история/визиты, очередь целей, прогнозы биологии, помощь со сбором, маршруты Spansh, POI, журнал находок, оценка непроданных данных. Основная ближайшая проблема — корректность истории и денег.
- **DSS:** экспериментальная включаемая подсистема. Native-marker FAST, событийный WGC, измерения Dispatcher/apply/render и сферические компоненты планировщика уже есть.
- **UI:** общие темы и ресурсы Compact/Minimal, RU/EN; ближайшие проблемы относятся к жизненному циклу операций, применению настроек и отдельным незавершённым переводам.

## Подтверждённые проблемы и доработки

Приоритет P1 — исправить до признания затронутого сценария стабильным; P2 — ближайший цикл стабилизации; P3 — улучшение качества/сопровождения. Проблемы экспериментальных функций помечены отдельно.

### M1 — P1: допустимый порог Mining может приводить к исключению

`MiningIntelligenceCalculator.cs:239` вызывает `Math.Clamp(value, Max(5, baseline-8), Min(60, baseline+8))`. При baseline >68 нижняя граница становится больше верхней. Например, baseline=75 даёт границы 67 и 60. Настройки допускают значения 0–100 (`SettingsService.cs:349`). Дефект проявляется после накопления достаточной выборки для adaptive advice.

Исправление: согласовать допустимый диапазон с расчётом и проверить границы 0/60/68/69/75/100 на достаточной истории. Это ошибка расчёта, а не недостаток внешних данных.

### M2 — P1: предполагаемое кольцо становится «подтверждённым»

`MiningRingContextService.cs:122` выбирает единственное кольцо с известными hotspots, даже когда у тела несколько колец. `MiningSessionService.cs:184` переносит это имя в сессию. Затем `MiningSessionDestinationLinker.cs:36,85` считает совпадение имени подтверждением места добычи.

Сценарий: у планеты A/B-кольца; просканировано только B, добыча фактически в A, точное имя текущего кольца ещё неизвестно. История может попасть в B с `Confirmed=true`. Это искажает personal quality и рекомендации следующих поездок.

Нужна явная достоверность происхождения места: наблюдаемое точное кольцо, пользовательское назначение, предположение по данным тела. Только первое либо отдельное подтверждение игроком должно давать exact-ring history. Тестировать multi-ring и смену колец внутри системы.

### M3 — P2: прогноз нехватки дронов математически подавлен

`MiningIntelligenceCalculator.cs:289` ограничивает `estimatedRequired` текущим количеством дронов через `Min(remaining, calculatedDemand)`. Затем проверяется `remaining < estimatedRequired`, что уже невозможно. Аналогично не работает относительный критический порог. Фактически остаются только абсолютные границы <8 и <=4.

Потребность для завершения добычи и доступный запас должны рассчитываться отдельно. Проверка: осталось 20 дронов, прогноз требует 50 — интерфейс обязан показать прогнозируемую нехватку.

### E1 — P1: частичная продажа обнуляет все непроданные исследования

`ExplorationEarningsService.cs:208,214` выполняет `bodyValues.Clear()` для обеих UC-продаж и `organicValues.Clear()` для каждой продажи биологии.

Сценарий: есть непроданные данные A и B, продано только A — оценка B пропадает. Текущие `ExplorationEarningsTests` закрепляют полное обнуление и требуют изменения вместе с реализацией.

Нужно сопоставлять состав фактической продажи с записями учёта. Для биологии нельзя обещать точную привязку каждой продажи к телу без достаточных идентификаторов; неоднозначный остаток должен явно оставаться оценкой. Нужны fixtures реальных SellExplorationData, MultiSellExplorationData и SellOrganicData, включая частичные и неоднозначные продажи.

### E2 — P1: история теряет текущий файл при перезапуске оверлея

`ExplorationJournalImporter.cs:27` исключает самый новый journal. `ExplorationHistoryService.cs:47` одновременно отбрасывает весь Bootstrap. Live accumulator не получает Commander/LoadGame/Location текущего файла.

Сценарий: запустить приложение посреди игровой сессии, затем прыгнуть/сканировать. Прошлая часть текущего файла отсутствует, новые строки могут записаться под `unknown` (`ExplorationHistoryRepository.cs:546`). Аналогичная потеря контекста возможна в `ExplorationLogService`.

Нужно обеспечить единого владельца обработки каждого события и идемпотентное восстановление текущего файла вместе с командиром/системой. Проверки: overlay restart без game restart, единственный journal-файл, ротация файла, смена командира, перезапуск мониторинга из настроек. До этого FIRST VISIT будет недостоверным.

### E3 — P2: неизвестное состояние открытия трактуется как первое открытие

Отсутствующие `WasDiscovered/WasMapped` превращаются в false в `JournalStateReducer.cs:885`, `ExplorationEarningsService.cs:229`, `ExplorationHistoryAccumulator.cs:33`. Внешние тела также создаются с false/false (`ExplorationSystemCatalogBuilder.cs:176`); очередь начисляет дополнительные приоритеты (`ExplorationVisitQueueEngine.cs:86`).

Нужны три состояния: неизвестно / ранее открыто / явно сообщено, что не открыто. История фиксирует first_* через MAX (`ExplorationHistoryRepository.cs:89`), поэтому замены типов недостаточно: требуется безопасное восстановление уже записанных ложных признаков из журналов с сохранением личных пометок.

### E4 — P2: учёт UC не сохраняет монотонность и не разделён по командиру

Повторный Scan после SAAScanComplete заменяет оценку картографирования оценкой сканирования (`ExplorationEarningsService.cs:231`). Полный replay читает все журналы каталога, а ключ учёта не содержит Commander/FID. Нет полной политики потери данных.

Разделить scan/mapping/acquisition/sale/loss и идентичность командира. Тесты: Scan → DSS → Scan; повторный replay; Scan после продажи; два командира; подтверждённые сценарии потери данных с учётом типа активности. Не расширять discovery UX до исправления этой модели.

### T1 — P2: реальный сбой bulk-market Ardent

В `overlay_log_2026-09-05_02-11-49.txt` семь предупреждений о преобразовании `$[0].marketId` в Int64, после чего поиск переключается на запросы по каждому товару.

`ArdentDtos.cs:72` требует `long`; `ArdentApiClient.cs:142` десериализует весь массив одной операцией. Допуск чисел в строках **уже добавлен**, поэтому повторное добавление AllowReadingFromString не является решением. В логе нет сырого ответа: null, дробное число и другие неверные формы пока не различены.

Получить ограниченный диагностический fixture ответа, валидировать строки отдельно и не придумывать marketId=0. Сейчас сырой ответ кэшируется до типовой проверки (`ArdentApiClient.cs:175`), поэтому ошибочный ответ может повторно ломать запрос до истечения TTL. Проверить смешанный массив с корректной и некорректной записью.

### T2 — P2: отмена Trade search не дожидается дочерних задач

`TradeSearchService.cs:194` создаёт SemaphoreSlim через using, запускает несколько задач и перечисляет результаты. При отмене/досрочном завершении async iterator семафор освобождается, пока незавершённые workers ещё выполняют `gate.Release()` (`:415`). Возможны faulted tasks и продолжающиеся сетевые запросы.

Нужны linked cancellation, отмена и ожидание всех workers в finally, затем disposal. Проверить закрытие поиска, смену активности и остановку перечисления без отмены переданного token.

### U1 — P2: Apply перезапускает журнал при несвязанных изменениях

`SettingsWindow.xaml.cs:224,348` всегда вызывает Restart при включённом журнале. Stop синхронно ждёт задачу до секунды (`JournalMonitorService.cs:60`), затем сбрасывается позиция чтения и начинается Bootstrap.

Изменение темы/хоткея либо повторный Apply может притормозить UI и запустить повторную обработку текущей сессии. Сравнивать старые и новые enable/path; применить настройки одной валидированной транзакцией, одной записью и одним уведомлением. Остановку фоновой задачи выполнять асинхронно.

`SettingsService.cs:104` пишет прямо в рабочий settings.json. При заполненном диске или сбое процесса это может оставить повреждённый файл. Нужны temp + атомарная замена, резервная копия и видимый результат сохранения. Сейчас при ошибке запись в лог есть, а полноценного результата для UI нет.

### U2 — P2: навигация может подтвердить старый маршрут и пережить закрытие окна

`EliteRouteNavigationService.cs:120` считает успехом наличие системы **в любой точке** Current.NavRoute. Это не доказывает, что построен новый маршрут к нужной конечной системе. Нужна проверка конечной точки и актуальности маршрута; отдельно обработать случай уже выбранного назначения.

У сервиса нет общего владельца единственной операции ввода. Параллельные команды из разных окон могут конфликтовать. `EngineeringWindow.OnClosed` отменяет engineerNavigationCancellation, но не materialTraderSearchCancellation/materialTraderRouteCancellation (`EngineeringWindow.MaterialTraders.cs:17`). Поэтому после закрытия помощника могут продолжиться действия с картой.

Нужны единая сериализация навигационных операций и отмена всех операций при закрытии их UI. Фиксированные координаты поля и ожидания результатов требуют live-проверки; автоматический режим сохраняет экспериментальный статус.

### X1 — P2: Mining-критическое предупреждение может не мигать на X52

`X52MiningCopilotFormatter.cs:120` задаёт мигание критической нехватки дронов через animationStep. Однако `X52IntegrationService.cs:151` прекращает обновлять animationStep без FSD/danger/low-fuel/overheat/SCO-событий. Само Mining-предупреждение таймер не активирует.

Проверять активные анимационные причины со всех модулей. Smoke: безопасная добыча, критический запас дронов, отсутствие остальных тревог — LED должен продолжать мигать.

### D1 — P2, experimental: шаг DSS может продвинуться по устаревшему MISS

`DssPrototypeController.cs:1193` продвигает цель при сохранённом `HudMissVisible=false` и доступной цели. Возраст наблюдения вычисляется/логируется, но свежесть не входит в это условие. При остановившемся захвате ранее допустимая цель может быть засчитана после реального ухода в MISS.

Добавить явные unknown/stale и проверку возраста наблюдения при fire. Не блокировать мгновенный NEXT AIM при свежем подтверждённом запуске. Распознавание визуальных изменений покрытия всё ещё требует проверки на достоверных событиях попадания.

Телеметрия уже есть: в логе 4 сентября, окно 18:25:24, applyAgeAvg=33,8 мс, renderAgeAvg=39,3 мс, dispatcherAvg=0,8 мс. Это один участок записанного прогона, а не измерение текущей игры или доказательство точности маркеров. Нулевые apply/render в других интервалах нельзя трактовать как нулевую задержку. Для дальнейшего DSS нужен replay с размеченными кадрами и сравнение ошибки позиции, выпадений и задержек p50/p95 на движении/остановке/реверсе.

### S1 — P2/P3: хранение и кэши имеют разные, неполные ограничения

- `ArdentRequestCache` хранит JSON в неограниченном словаре. Истёкшая запись удаляется только при обращении к тому же ключу. Смена систем/фильтров накапливает данные в RAM за всю сессию. Нужны лимит записей/байт и периодическое удаление истёкших элементов.
- `FsdScoCooldownResearchLogger` вызывается при изменении Status.json до обычного разбора, синхронно дописывает полный JSON без общего лимита/опции. В последнем логе 12 предупреждений о пустом JSON во время записи игрой. Старый `FsdScoResearchLogger` не используется production-кодом.
- Обычный `Logger.cs:19` пишет рядом с exe и AutoFlush=true. Installer ставит приложение в Program Files; стандартный запуск может остаться без файлового лога из-за прав. Перенести в LocalAppData, добавить ротацию и неблокирующую очередь.
- DSS уже имеет retention 768 → 640 MiB при старте сессии. Но он обходит все подкаталоги корня; стоит ограничить удаление узнаваемыми собственными сессиями, учитывать текущую сессию и защищённые калибровочные данные.
- `StorageUsageService` считает всю LocalAppData-папку «кэшем», а кнопка очистки удаляет лишь exploration-system-cache. Пользователю нужны отдельные категории cache/research/logs/history и соответствующие правила.

На момент аудита: companion.db около 0,71 MiB; exploration-system-cache около 0,83 MiB; Research около 625,53 MiB, из них DSS 624,76 MiB и FSD-SCO 0,77 MiB. Нет оснований считать маленькую SQLite-базу причиной заполнения C:. Историю/закладки не следует удалять для лечения размера кэша.

## Как изменить предложенный план

1. **Stabilization / merge-prep:** исправить M1–M3, X1, T1–T2, U1–U2; убрать мёртвый SCO logger и связанный obsolete test либо вывести диагностическое логирование под явную опцию/лимит. Удалить LESS dump. Сохранить обозначение SCO как приблизительной оценки; имя `ScoEstimatedCooldownUntilUtc` делает ограничение понятнее.
2. **Exploration correctness — до новых badges:** E1–E4, текущий journal/bootstrap, идентичность командира, монотонность оценки, неизвестные поля и восстановление исторических флагов. Это отдельный набор небольших проверяемых исправлений; его не стоит откладывать за разработку новых функций. Если Mining сливается раньше, эти дефекты должны быть явно отражены как ограничения базовой версии.
3. **Merge gate:** CI на feature-push добавить до слияния, согласовать SDK для локальной и CI-сборки, Release + все тесты + live-матрица ниже. PR в master полезен как проверяемая точка интеграции. Не удалять ветки только по возрасту: проверить, вошли ли их изменения, включая локальные коммиты.
4. **Exploration discovery-status:** FIRST VISIT/дата прошлого посещения, FD/FM candidate, фильтры. Показывать отсутствие данных в доступной личной истории, состояние импорта и явное Journal false; отсутствие записи Spansh/EDSM не означает отсутствие других игроков. Снимок прошлого посещения получить до обновления записи текущим прибытием.
5. **Mining personal intelligence v2:** после достоверного exact-ring history вводить вес личной статистики по объёму/качеству выборки; показывать samples/confidence, sessions, hit-rate, median/average content и tons/hour. Базовые данные уже есть, ещё один provider не является необходимым первым шагом.
6. **Trade refinement:** profit/hour, station-LS и confidence уже реализованы в `TradeTravelTimeEstimator`, `TradeRouteConfidence` и сортировке workspace. Дальше — калибровка по реальному времени рейсов и продажам, улучшение отбора кандидатов, устойчивость provider/cache/отмены и понятные причины плохого рейтинга.
7. **Engineering:** сохранить текущую архитектуру; закрыть жизненный цикл навигации/поиска и локализацию. Затем — конкретные правила добычи и оптимизация нескольких последовательных целей по обратной связи игрока.
8. **DSS отдельным циклом:** stale-MISS gate, повторяемый CV replay и измерения ошибок. Новую смену рендера, дополнительный predictor или замену плана выбирать по измерениям актуальной версии.
9. **Release-prep:** install/upgrade обычным пользователем, writable logs/settings, версия схемы + backup перед миграцией, восстановление без старых журналов, комплект runtime/data/docs, README/screenshots/changelog, явный experimental статус DSS/автонавигации.
